第 3 章 v2 引擎：DI × Scope 新架构

研究对象：packages/agent-core-v2（约 10.6 万行 TS，src 下 16 个一级目录、约 750 个文件）。这是 Kimi Code 的当前主架构，本书篇幅最重的一章。 学习目标：理解"作用域即架构"的四层 LifecycleScope 树、回合主循环、工具/权限决策链、wire 可重放状态机与全量压缩。

#3.1 定位与四层作用域

@moonshot-ai/agent-core-v2 是 Kimi Code 的第二代统一 agent 引擎（"The unified agent engine for Kimi (v2 — DI Scope architecture)"），承载从 LLM 请求、回合循环、工具执行、权限审批，到会话/工作区/持久化/协议适配的全部核心能力。它是 kap-server 背后的引擎，也是 klient（客户端 SDK）与 kimi-inspect（调试台）的契约来源。

引擎边界：agent-core-v2 只提供"能力与生命周期"，不提供传输。REST/WS 由 kap-server 承担；引擎内 app/gateway 只是把 RPC 语义翻译成原生调用的边缘适配层。

#3.1.1 四个作用域层

层 生命周期 代表服务
App（app） 进程级，Scope.createApp bootstrap、config、workspace 注册表、workspaceLifecycle（handler 注册表）、feature manager、telemetry、auth
Workspace（workspace） 每工作区一个 handler，create-or-get、永不关闭（随 App 级联销毁） workspaceContext/Fs/Git/Process/Mcp/McpConfig/SkillCatalog/ToolPolicy/Trust、sessionLifecycle
Session（session） 会话开闭（create/resume/fork/close/delete/archive） agentLifecycle、sessionMetadata、interaction、approval、question、subagent、btw、todo、terminal
Agent（agent） 每 agent（main/sub）一个，wire.seal→restore→bind→activate loop、prompt、llmRequester、contextMemory、toolRegistry/toolExecutor、permissionGate、profile、rpc、undo、fullCompaction

拓扑由模块副作用 setScopeTopology(SCOPE_TOPOLOGY) 声明（app/scopes.ts:26）；Scope.createChild 强校验 kind 必须严格大于父层，同一 id 的子 scope 重复创建抛错。

为什么四层作用域：资源拥有者决定生命周期。workspace 资源（fs/git/MCP/技能目录）按 handler 加载一次、多会话共享、fs-watch 刷新；Session 资源（interaction/cron/metadata）随会话开闭；Agent 资源（loop/上下文/工具表）随 agent 生灭。没有 App 级会话门面——调用方必须组合 ISessionIndex → IWorkspaceLifecycleService.handlerFor → workspace 的 sessionLifecycle。

#3.1.2 与 v1 / kap-server / kosong 的关系

  • 与 agent-core（v1）：同仓并存、WIP port（AGENTS.md 明示 "work-in-progress port of packages/agent-core"）。二者共享磁盘布局（workspaces.json、state.json、session_index.jsonl），v1 TUI 与 v2 服务器可共存读写（workspace 注册表因此"无内存写缓存"）。
  • 与 kap-server：kap-server 只 import 其公共面；transport/mainAgent.ts 直接 re-export ensureMainAgent/MAIN_AGENT_ID——会话创建时没有 main agent，首次请求按需物化。
  • 与 kosong：src/kosong/ 是独立包 packages/kosong 的 DI-Scope 重构版（不是依赖关系）——契约→协议 trait 注册表→模型目录→供应商基座四层。

#3.2 DI Scope 内核（_base/di/）

#3.2.1 注册与创建

  • registerScopedService(scope, id, ctor, activation, domain)（scope.ts:54）写入进程级注册表——模块加载即注册（import = register），因此 index.ts 全部是 re-export + 裸 import。
  • Scope.createApp / createChild 是仅有的 scope 创建点：构造 ServiceCollection（extra seed 覆盖注册表）→ createChild → watchScopeUnits（物化该层 ScopeUnits(kind) 记录）→ options.assemble（session seed 适配器挂钩点）→ provideScopeServices（把该 kind 全部注册作为一个级联事务 provideAll 提交）→ 立即激活 OnScopeCreated 服务。激活失败整体 dispose 回滚。

#3.2.2 Service 单元：两阶段构造

Service 基类（extends Disposable），能力都在 this 上：provide/effect/on/get/ref。两阶段构造：ctor 内 provide/on/effect 只是缓冲（get/ref 会抛错，依赖全部走构造参数装饰器）；内核在 Reflect.construct 后绑定运行时、按写入序 flush；手动 new 的实例任何能力调用都抛错。

#3.2.3 Fiber 五态机与级联引擎

                        ┌───────────── 传染集（依赖图可达闭包）─────────────┐
provide(unit) ──► 事务开始 ──► abort hook（veto）──► 全局逆拓扑 teardown
                        │  （卸载依赖此单元的单元）
                        ▼
                   apply 变更 ──► 等待区重查（依赖已满足的挂起单元自动激活）
                        │
                        ▼
                   FiberState: Pending → Activating → Active → Unloading → Failed
                        │             ▲              │           │
                        │             └── 依赖到达(跨 scope) ──┘           │
                        └── 构造失败 = sticky Failed（不自动重试；update() 重载）
  • 为什么构造失败 sticky：不自动重试（重试风暴）；update() 显式重载；解析 Failed 单元 rethrow 原错误——错误可见且可诊断。
  • collection 贡献点：collection<T>(name) token——把"一组同类贡献"声明为 token（AgentToolContribution/WireModelContribution/ConfigSectionContribution/AgentProfileContribution），消费方拿 CollectionView<T>（items/records/增量 onDidChange）。可见性规则：provider 的祖先与后代可见，兄弟子树不可见；provider 死亡即撤回。
  • Feature 连坐：Feature 单元的所有贡献挂在它自己的账本上，撤回 Feature 单元即撤回全树贡献；plan 是第一个按此模式提取的内置 Feature。
  • 快照安全纪律：可快照的纯数据（state 键）注册进 I{App,Workspace,Session,Agent}StateService；含函数引用的机制字段留在实例字段。snapshot() 用 toJsonSafe 把自定义原型对象折叠为 '(ClassName)'——防止顺着服务引用把整个 DI 图拷到堆爆。

#3.3 回合主循环（agent/loop/）

#3.3.1 请求队列 + 惰性物化

调用方（prompt 服务 / steer / 外部 hooks / goal 调度 / task 通知）
   │  new MessageStepRequest(msg) / ContinuationStepRequest / SteerStepRequest
   ▼  IAgentLoopService.enqueue(request, {at})          （admission 决定去向）
TurnJob.queue（StepRequestQueue）
   │  beginLoopStep → takeNextBatch() = {driver + merged[]}
   ▼
materializeBatch ──► 每个 request：onWillMaterialize → resolveContextMessages() → context.append()
   │                  （消息此刻才进 ContextModel；aborted 请求在此前被丢弃，上下文零污染）
   ▼
onWillBeginStep hooks（contextInjector 注入 / fullCompaction beforeStep / stepRetry 复位）
   ▼
llmRequester.start({source:{type:'turn',turnId,step}}, streamParts, signal)
   │  resolveRequest：turn 配置快照 → completion 预算折叠 → requester → tools shape
   ▼
runRequest（投影 normal/media-degraded/media-stripped/strict 选择 + 降级重发循环）
   │  for await (requester.request(...))：
   │      'part' → onPart：assistant.delta / thinking.delta / tool.call.delta 事件
   │      'usage' → 暂存；'finish' → 记录 message/traceId
   ▼
loop.executeLoopStep
   ├─ appendResponseContent：每个 content part → context.appendLoopEvent('content.part')
   ├─ executeStepTools：toolExecutor.execute(toolCalls) → appendLoopEvent('tool.call'/'tool.result')
   │      stopTurn → finishReason='completed'（否则 'tool_calls' → 下一轮）
   └─ finishStep：appendLoopEvent('step.end') + turn.step.completed 事件
   ▼
onDidFinishStep hooks → 队列空 → turn 完成
   ▼
releaseActiveTurn → wire.dispatch(endTurn) → turn.ended 事件 → pumpTurns（下一个 Turn）

关键契约：

  • StepRequest（stepRequest.ts:40）：admission（newTurn|activeOrNewTurn|activeOrNextTurn|activeTurnOnly）决定去向；状态机 pending→materialized|aborted。惰性物化：resolveContextMessages() 在 pop 时才调用，aborted 请求不触碰上下文（零污染、无需补偿 undo）。
  • takeNextBatch：driver + 所有可合并请求（steer/task 通知）折叠进同一 LLM 请求——省 token 省往返。
  • turn 快照：prepareTurnConfig 冻结 systemPrompt/params，同一 turn 的重试共享配置——中途换配置不可复现。
  • loop 自己从不 enqueue，只跑请求和分发错误。错误处理走注册的 LoopErrorHandler 链（first-match wins）：stepRetry（可重试错误退避重排队首）、fullCompaction（context overflow 恢复）。LoopErrorContext 含 retry(request) 闭包——恢复插件唯一的重新排队通道。
  • tryAcquireQuiescence（:271）供 undo/compaction 在空闲窗口加锁（quiescence 期间新请求进 heldAdmissions，释放后按序补投）。
  • maxSteps：loop_control.max_steps_per_turn 超限抛 LOOP_MAX_STEPS_EXCEEDED。

#3.3.2 错误与 abort 契约

  • 错误分类在 kosong/contract/errors.ts：isRetryableGenerateError = 连接/超时/空响应/overloaded/[408,409,429,500,502,503,504,529]；quota_exhausted 与图片格式错不可重试。
  • abort 契约：generate() 在每个 part 前后查 signal 并 cancelStream；错误转换器第一行必须 throwIfAbortError——用户取消永不被误分类为可重试 provider 错误。

#3.4 上下文折叠（loopEventFold）

ContextModel + 5 个 Op：append_message/append_loop_event/clear/apply_compaction/undo。

step.begin ──► settleOpenStep（上一 step 未 settle 先补）──► 开 partial:true assistant
content.part / tool.call ──► 追加进打开的 assistant
tool.result ──► push tool 消息；pending 记账（非空时 append_message 被 deferred）
step.end ──► closePending（中断 tool call 补 <system>Tool execution was interrupted... 错误消息）
             ──► 无 toolCalls 且内容全 vacuous → 整条丢弃（否则违反 provider 消息校验）
             ──► 否则 partial 封口
clear / apply_compaction / undo ──► resetFold（折叠态清零）
  • live 与 replay 共用同一归约（v1 磁盘格式字节兼容）。
  • 折叠上下文存 WeakMap<stateArray, FoldCtx>——并发还原不同 Agent 不串扰。
  • contextTranscript.ts 是第二归约器：从 journal 重建全量显示历史（含被压缩掉的部分，供 /messages）。
  • computeUndoCut（:308）：撤销切割算法——从尾向前数 isUndoAnchor（user 消息 / user-slash 触发的 skill_activation、plugin_command），跳过 injection，遇 compaction_summary 停。
  • blob 编解码：超大 data URI 经 dehydrate/rehydrate 搬运到 blobref:。

#3.5 工具系统（agent/tool*）

#3.5.1 基础契约（tool/toolContract.ts）

  • ExecutableTool<Input>：resolveExecution(input) 是唯一入口；RunnableToolExecution 携带 accesses/approvalRule/matchesRule/display/stopBatchAfterThis/execute。
  • ToolAccesses（none/all/file(op,path,{recursive})）+ conflict() 冲突语义：仅"至少一方写 + 路径重叠（同路径或 recursive 前缀）"才冲突，路径判定小写化+分隔符归一——读类工具天然并行，写类串行。
  • 注册双通道：registerAgentToolService(id, ctor, {name, source, disclosure, when, domain}) = 静态模块表 + Agent 级 OnDemand 注册；built-in 由 App 级 builtinToolAssemblyService 一次性提供。

#3.5.2 执行管线（toolExecutorService.ts，985 行）

LLM toolCalls[] → loop.executeStepTools → toolExecutor.execute(calls)
   [preflight] parse args → resolve → ToolCallGuard（toolPolicy 兜底）
              → AJV 参数校验（WeakMap 缓存 validator，$schema 自动选 draft）
   [prepare×N 顺序] resolveExecution(args) ← 工具返回 accesses/approvalRule/execute
              → onBeforeToolExecute veto 事件 ← permissionGate 在此裁决
              → onWillExecuteTool waitUntil（MCP 首载等就绪工作）
              → tool.call.started 事件 → task = {accesses, execute}
   [executeBatch] ToolScheduler：冲突串行、不冲突并行；按完成顺序 yield
              → execute(ctx)：onUpdate → tool.progress 事件；raceWithAbortGrace（2s 宽限）
   [finalize] onDidExecuteTool hooks（可改写 result/置 stopTurn）
            → resultTruncation.truncateForModel（>50k 落盘 + 2k 预览 + output_path）
            → tool.result 事件

边界处理：

  • veto 事件链（beforeToolExecuteEvent.ts）：立即语句 veto（首个生效）/allow（终局）/pass（放行留 trace）/waitUntil（冷工厂，仅当所有 listener 未 veto/allow 后才调用——审批不发空枪）；closeRegistration() 后异步调用即抛。
  • abort 2 秒宽限（raceWithAbortGrace）：abort 后不立即杀结果等待，先给工具 2s 自行收敛。
  • preflight 拒绝 ≠ 异常：所有准备期失败转成 isError 合成结果，照常发布 tool.call.started/tool.result——模型可见、流不中断。
  • stopBatchAfterThis：prepare 顺序 await，一旦声明则其后所有调用标 skipped——"决定串行、运行并行"。
  • 去重（toolDedupe）：同 step 重复调用 veto 占位（结果广播给所有副本）；跨 step 连续重复 3/5/8/12 档 system-reminder，12 次强制 stopTurn。
  • 路径安全：纯词法 canonicalize（不跟 symlink）；isWithinDirectory 要求分隔符前缀防 /workspace-evil 共享前缀逃逸；敏感文件判定含 .env/SSH key 及变体，豁免 .env.example/id_rsa.pub。
  • 渐进式工具披露（toolSelect）：shapeTools（deferred 标记）/shapeHistory（剥离未激活工具 schema）/load（schema 注入 contextMemory，无独立持久化账本，靠重折叠历史自愈）。

#3.6 权限与审批

#3.6.1 12 策略静态链（permissionPolicyService.ts:46）

1 auto-mode-ask-user-question-deny（auto 禁 AskUserQuestion）
2 user-configured-deny（turn-override/project/user 作用域）
3 auto-mode-approve
4 session-approval-history（"approve for session" 记忆 → 直接批）
5 user-configured-ask
6 user-configured-allow
7 sensitive-file-access-ask（.env/SSH key/密钥变体）
8 git-control-path-access-ask（.git/工作树控制文件）
9 yolo-mode-approve
10 default-tool-approve（内置白名单：Read/Grep/Glob/WebSearch/…）
11 git-cwd-write-approve（工作区 git 仓库内 Write/Edit）
12 fallback-ask（兜底问用户）

策略链的顺序是语义：auto-deny 必须在 auto-approve 前、用户 deny 在用户 allow 前、session 审批记忆在 user-configured-ask 前（"已批准过"优先于"默认问"）。首个非 undefined 胜出。

  • permissionGate 注册为 veto listener，把决策翻译成事件语句。
  • harness 约束（plan guard、swarm 批量互斥、btw deny、goal 护栏）不混入权限链，各自注册独立 veto listener——gate 只裁决"风险"，产品约束可独立演进。
  • 审批往返（toolApproval）：经 session/approval broker（interaction kernel kind='approval'），approved+session 作用域时记录工具 approvalRule 串（recordApprovalResult 是持久化 wire op，replay 后依然生效）；用户 [permission] 规则是 transient（宿主 resume 时重供）。
  • 规则匹配：Tool(args) pattern → 纯名/带参；工具名 picomatch glob；带参时调用工具自带 matchesRule 主题谓词（Bash("npm *") 可匹配任意 npm 命令，Bash("npm test") 只匹配字面）；! 前缀取反。
  • 三层工具可见性：Profile ∩ 全局 [tools] ∩ Session denylist（activation 期 registry + 执行期 ToolCallGuard + 模型可见性 shapeTools 三层各自把关）。session denylist 显式空列表绝不禁用一切。

#3.7 全量压缩（fullCompaction）

wire CompactionModel：idle ⇄ running（begin/complete/cancel 三 Op；崩溃遗留 running 由 onDidRestore 归 idle）

触发：① auto：每 step 前 checkAutoCompaction（used ≥ max×triggerRatio(0.85)）
     ② overflow：loop 错误处理器 recoverFromContextOverflow（CONTEXT_OVERFLOW | 413 且估算≥max×0.5）

compactionRound：
  1. hooks.onWillCompact
  2. 组装压缩专用请求（显式 messages=[history, user(instruction)]，maxOutputSize=min(max,128KiB)）
  3. collectSummary（truncated → CompactionTruncatedError；空 → APIEmptyResponseError）
  4. 失败分流：overflow → observeContextOverflow(估算×0.85) → shrink（0.7/0.5/0.35，≤3 次）重发；
     truncated/empty → 丢最旧消息（≤5 次）；retryable → 指数退避（≤5 次）
  5. historySafeToCompact：压缩期间历史被并发 append（引用变化）→ 取消压缩，绝不覆盖新输入
  6. postProcessSummary：追加当前 TODO List
  7. context.applyCompaction：buildContextCompactionShape ——
     真 user 消息按 20k token 预算选 head(≤2k)+tail（跨界消息尾部截断、前缀进 head 候选），
     中间插 elision system reminder；末尾追加 compaction_summary user 消息；
     injection/shell/task/cron/hook/retry/team 来源消息全部丢弃
     → wire apply_compaction + context_size.measured + context.spliced
  8. profile.refreshSystemPrompt → contextInjector.injectAfterCompaction
  9. wire full_compaction.complete → compaction.completed 事件
  • 上下文溢出观测学习：observeContextOverflow(估算×0.85)——把实际超限当作校准信号，估计值打 0.85 折记为真实窗口，后续自动压缩更早触发。
  • 压缩并发安全：historySafeToCompact 逐引用比对（压缩期间用户新发消息 → 取消本次压缩）；未阻塞 turn 的压缩失败不影响回合，被阻塞的失败使回合失败。
  • 防抖：lastCompactedTokenCount——上下文没增长不重复压缩；每 turn 重置计数。
  • 手动压缩要求 loop idle；被 turn 阻塞时 blockedByTurn=true，turn abort 级联压缩 abort。

#3.11 kosong：LLM 抽象（src/kosong/）

src/kosong/ 是外部 packages/kosong 的 DI 分层重构（contract → protocol → model → provider）：

  • contract：纯类型+纯函数（与外部包逐行同构）；errors.ts 的错误分类（isRetryableGenerateError 等）。
  • protocol：ProtocolTrait 16 个全可选 hook——管道型（convertMessage/mergeHistory/buildParams）按 trait 序链式（任一返回 null 即丢弃消息），单值型（convertTool/convertError/withThinking/cacheKey/extractUsage）last-declarer-wins。

  • tool-call id 归一：[^a-zA-Z0-9_-]→_ 清洗 + 上限截断（Anthropic 64）+ 全历史一致重写 + _2/_3 后缀保唯一。
  • ReasoningKeyDialect：入站按 reasoning_content → reasoning_details → reasoning 优先级探测并记住该 endpoint 实际说的方言，出站回显。

#3.12 持久化（persistence/）

  • L0 字节层：IFileSystemStorageService 只有 write（原子替换）与 append（有序追加）两个原语；原子写 = tmp + fsync + rename + 目录 fsync（每进程每目录一次，Windows 跳过 + rename 前先 unlink）。
  • AppendLogStore（WAL 语义）：每 (scope,key) 一个 LogState；append 同步入队 + microtask 合批；read 先 flush（read-your-writes）；torn 行容忍（末尾无换行残行静默丢弃，中间损坏抛错）；sticky failure——flush 失败置位后后续 flush 全部立即 reject（不猜"是否已提交"，防重复写），唯一恢复是成功 rewrite；cutoverEpoch 版本号让 rewrite 与并发 append 交接不丢序。
  • AtomicDocumentStore：每 (scope,key) 一个类型化值全量替换；JSON/TOML 双 codec。
  • QueryStore（minidb 后端）：ClusterDb 16 shard、多进程读写（单 shard 单写者）；collection 编码为 collection+NUL+key 物理前缀；损坏 → 进程内一次性 rebuild。
  • 写路径纪律（AGENTS.md 强制）：业务域不实现持久化，只依赖按访问模式命名的 Store；禁止业务代码 import 'node:fs'。

#3.13 配置分层（app/config/configService.ts）

五份视图：rawSnake（磁盘原样）→ raw（camelCase，env-free）→ validated（schema 校验，env-free，永不改——env 退化时回落到文件值）→ effective（env 叠加后，每次现算）→ memory（进程内覆盖，get 优先）。分层：defaultValue → config.toml → env → memory；workspace 层不在 ConfigService（项目级在 local.toml）。

#3.15 本章小结

  • 作用域即架构：App → Workspace → Session → Agent 四层 LifecycleScope 树 + Fiber 五态机 + 级联事务；一切能力都是可挂账本、可撤回、可内省的 DI 单元——"注册的服务就是公共契约"。
  • 回合是"请求队列 + 惰性物化"的产物：StepRequest 在 pop 时才把消息 append 进 ContextModel，aborted 请求零污染；流式事件经 loopEventFold 实时折叠成消息，live 与 replay 共用同一归约。
  • 一切可重放状态走 wire journal：undo/压缩/续会话全部是对日志的确定性重放；上下文压缩有观测学习（×0.85 校准）、并发安全（historySafeToCompact）、输入阶梯（verbatim→fitted→lossy）。
  • 工具执行是 veto 事件链 + 冲突感知并发：权限裁决挂在执行器上（审批不发空枪），12 策略链只判"风险"，harness 约束各自注册独立 veto listener；读写冲突判定让读类工具天然并行、写类串行。
