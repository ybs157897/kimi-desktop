第 4 章 v1 引擎：上一代内核

研究对象：packages/agent-core（约 6.9 万行 TS，371 个文件）。 学习目标：理解 v2 的"前传"——VSCode 风格手写 DI 容器、无状态纯循环、事件溯源式持久化。读 v1 是理解 v2 的捷径：v1 定义的概念（loop 契约、wire record、RPC 面、Hook 语义）是 v2 的直接前身。

#4.1 定位：被 v2 取代，但绝非死代码

agent-core 是 Kimi Code 历史上第一个"统一 agent 引擎"（"The unified agent engine for Kimi"）。它把 agent 运行时的全部要素收拢在一个包里：Agent 聚合根（20 个子管理器）、无状态主循环、会话与持久化、宿主 RPC、DI 容器、MCP/插件/技能/内置工具。

与 agent-core-v2 的关系（证据链）：

  1. 主应用用 v2：apps/kimi-code 依赖 agent-core-v2，不依赖 agent-core。
  2. agent-core 的现存消费者：node-sdk（双引擎兼容层）、acp-adapter（仍跑 v1）、apps/vis/server、migration-legacy。
  3. v1 仍承担"用 v2 写出的会话文件恢复旧引擎"的兼容职责：restoreAgentRecord 显式处理 v2 引擎写入的 profile.bind（映射为 v1 的 config.update + tools.set_active_tools）等 record 类型。

一句话：agent-core 是 v2 的"上一代内核"，负责 SDK 嵌入、ACP 与迁移场景。

#4.2 手写 DI 容器（di/，约 600 行零依赖）

设计动机（di/README.md）：零运行时依赖 + 与 VSCode vs/platform/instantiation 概念对齐。

概念 语义
createDecorator<T>(name) 铸出"品牌化可调用值"作为服务标识；同名幂等（同一 name 返回同一引用）；同时是构造器参数装饰器
SyncDescriptor<T> 包装构造器 + 静态参数 + supportsDelayedInstantiation 标志
ServiceCollection 每容器一份 id → (descriptor|实例) 映射
InstantiationService 运行时容器：解析、缓存、子容器、追踪、销毁
registerSingleton 模块级全局注册表（import barrel 即触发副作用）
Graph<T> 依赖子树，用于环检测 + 叶子优先构建

注入模型：构造器参数按序解析——非装饰静态参数在前、@IFoo 装饰的服务参数在后。

延迟实例化（Proxy 魔法）（instantiationService.ts:426-537）：首次 accessor.get(IFoo) 返回 Proxy(Object.create(null))，真实构造器不执行；Proxy 的 get trap 把 onDid*/onWill* 属性访问"驻车"进 LinkedList 早监听器；首个非事件属性访问触发真正构造，随后重放驻车监听器；getPrototypeOf trap 返回真实 ctor 的 prototype——instanceof 可用。

环检测双保险：

  1. 图遍历（主）：先用 getServiceDependencies 构建完整依赖子树（Graph），然后反复取 roots() 叶子优先构造；图卡死（非空无根）抛 CyclicDependencyError，findCycleSlow() 格式化 A -> B -> A 路径——任何构造器体运行之前就能抓到环；
  2. 树级构造栈（防御）：根容器持有 _inProgress 栈，抓构造器体内 accessor.get 互相回调产生的运行时环。

#4.3 loop：无状态主循环

设计原则（loop/README.md）：loop 不持有会话、wire 传输、压缩执行、权限 UI、协议桥——这些全是宿主层职责；loop 与宿主之间只通过窄接口通信。

文件 职责
types.ts LoopHooks（6 个阶段钩子）、ExecutableTool、TurnResult、LoopStepStopReason
llm.ts LLM 接口：systemPrompt/modelName/capability/chat()
events.ts 事件双路：LoopRecordedEvent（step.begin/end、content.part、tool.call/result——入转录本）与 LoopLiveOnlyEvent（delta/progress/retrying——只直播）
run-turn.ts 回合收敛：abort 安全点、maxSteps、usage 聚合
turn-step.ts 单步：beforeStep 钩子、消息构造、LLM 调用、流式回调、工具批次交接
tool-call.ts 工具调用批次生命周期（preflight → prepare → 调度 → tool.result）
tool-scheduler.ts 有状态调度器：资源访问不冲突的任务可重叠执行，冲突任务按 provider 顺序串行
retry.ts 指数退避重试（500ms×2^n 封顶 32s、±25% 抖动、Retry-After 覆盖）
tool-access.ts ToolAccesses：文件级读写/search 资源声明 + conflict() 判定

LLM 与 ExecutableTool 是宿主与 loop 的全部边界：宿主提供 buildMessages、buildTools、dispatchEvent、hooks，loop 不 import 任何宿主实现。

要点：

  • buildTools 在 beforeStep 之后求值：beforeStep 可能跑压缩（丢弃动态工具 schema），提前快照会派发模型已没有的工具。
  • 工具批次按 provider 顺序落事件：执行可乱序完成，但 tool.result 严格按 provider 顺序 await 分发，且每对 tool.call 必有配对 tool.result。
  • 中断语义：turn.interrupted 事件在 step.begin 存在而无 step.end 时仍正确报告；usage 在 llm.chat 返回后立即记账（工具执行中途 abort 不丢已耗 token）。

#4.4 Agent 聚合根

Agent（agent/index.ts:115）构造器把 20 个子系统一次性组装：

records / fullCompaction / microCompaction / context / config / turn /
injection / permission / planMode / swarmMode / usage / skills / tools /
background / cron(仅 main) / goal / replayBuilderts

关键设计：

  • AGENTS.md 硬性规则：Agent 构造器不得强制要求 Session/agentId——保证 Agent 可独立运行。
  • Agent.generate 是闭包包装（:288）：在 kosong generate() 前挂上 LLM 请求日志、请求记录（wire record）、认证解析（modelProvider.resolveAuth）；abort 预检避免记录未发出的请求。
  • Agent.rpcMethods（:550）：把全部 RPC 方法映射到内部管理器——这是 rpc/core-api.ts 的 AgentAPI 实现。
  • toolSelectEnabled（:279）：渐进工具披露的三门闸（模型能力 dynamically_loaded_tools ∧ tool_use ∧ tool-select 实验开关）。

TurnFlow（agent/turn/index.ts:139）是回合的"宿主侧"编排：

  • steer()：活跃回合或手动压缩期间缓冲（steerBuffer），onCompactionFinished 重放；
  • cancel()：以 userCancellationReason() 作为 signal.reason abort——一路传给工具，让模型能区分"用户主动打断"与"系统超时"；
  • turnWorker：有活跃 goal 则走 driveGoal（每回合重新注入 GOAL_CONTINUATION_PROMPT），否则 runOneTurn；
  • runOneTurn 永不 throw，异常映射为 cancelled/failed；
  • runStepLoop 实现宿主侧全部 6 个钩子：beforeStep（压缩）、afterStep（usage/compaction/goal 预算 stopTurn）、shouldContinueAfterStop（4 级继续决策：goal 预算硬顶 → steer 冲刷 → print 模式排空 → Stop 钩子一次续跑）、prepareToolExecution（同步去重）、authorizeToolExecution（权限）、finalizeToolResult（去重登记、PostToolUse 钩子、预算裁剪）。

#4.5 ContextMemory：历史状态机

不变量：历史尾部不得存在未闭合的工具调用交换——pendingToolResultIds 记录尾部缺失的 tool result，后续消息进 deferredMessages 直到补齐。

                    ┌─────────────────────────────────────────────────┐
                    │ _history: ContextMessage[]                      │
                    └─────────────────────────────────────────────────┘
      不变量: 尾部不得有未闭合工具交换
      新消息 → 若 pending 非空 → 进 deferredMessages，直到对应 tool.result 补齐
                     │
   appendUserMessage │ appendLoopEvent(tool.call/result/step.end) │ applyCompaction
   (origin 标记)      │ (折叠为 ContextMessage)                     │ (head+tail 保留+摘要)
                     ▼
            投影层 projector.ts（每次请求构建，不落盘）:
              project() ── 媒体降级、孤儿 tool result 丢弃、尾部未闭合交换裁剪
              strictMessages ── 严格线规重排（闭合工具调用、合并连续 assistant）
              mediaDegradedMessages / mediaStrippedMessages ── 媒体投影
  • 消息带 origin（user/injection/retry/compaction_summary/shell_command/plugin_command/hook_result/system_trigger…），决定 replay 是否可见、undo 是否可删、投影是否进请求。
  • undo(n) 从尾部删到第 n 个真实用户输入，遇压缩摘要边界停；injection origin 的消息不可撤销。

#4.6 容错与重试体系（三层防御）

  1. step 层：chatWithRetry 默认 10 次尝试（9 次重试），退避 min(500ms × 2^n, 32s) + 25% 抖动，Retry-After 覆盖本地退避；每步发 step.retrying 直播事件。
  2. 消息投影重发（turn-step.ts:209-391，v1 最精细的恢复机制）：
    • 413 请求体过大：normal → media-degraded → media-stripped 逐级降级重发，且一旦某级成功，回合内后续 step 直接使用该投影（避免每步重复被拒）；
    • 图片格式被拒（不知道哪张图有毒）：整体换文本标记重发一次——"唯一保证无毒的投影"；
    • 结构非法（tool_use/tool_result 配对、空文本、角色不交替）：buildMessagesStrict 严格重建重发一次，仍被拒则大声报错（wire 合规性缺口信号）。
  3. 上下文溢出（turn/index.ts:1027）：APIContextOverflowError 或 413+估计超窗 → 观测学习实际窗口（observedMaxContextTokensByModel = 估计 × 0.85）→ 强制压缩 → 重试；连续 3 次失败放弃抛 CONTEXT_OVERFLOW。

三层防御保证"同一段历史不会被 provider 反复拒绝而死循环"。

#4.7 工具执行的安全与信任边界

  • coerceToolResult（tool-call.ts:686）：工具是任意 JS，返回值经信任边界校验——null/undefined、非对象、缺 output 字段一律转 isError 结果，保证 tool.result 事件永远配对合法。
  • normalizeToolResult：空输出替换为 'Tool output is empty.'；stopTurn/message 是循环内私货，持久化时剥掉，只保留 note（模型可见侧信道）。
  • 2 秒宽限超时：abort 后工具若无视 AbortSignal 不收敛，raceExecuteWithGraceTimeout 用 2s 哨兵兜底返回合成错误。
  • abort 文案区分：isUserCancellation(signal.reason) 时明确告诉模型"用户主动打断，不要自动重试"。
  • 未执行工具调用（recordUnexecutedToolCalls）：provider 流中断但响应仍带 toolCalls（参数可能截断）——不执行但也不丢弃：逐条记录并立即闭合合成错误结果，保持 wire 合法、不丢模型意图。
  • stopBatchAfterThis：工具成功返回 stopTurn 后，同批次的后续调用全部跳过，但仍记录 tool.call+tool.result 配对。

内置工具全清单（agent/tool/index.ts:775，约 25 个）：文件（Read 1000 行/100KB、Write、Edit replace_all+CRLF、Grep rg 子进程、Glob、ReadMediaFile）、Shell（Bash 前台/后台/超时自动转后台）、规划（EnterPlanMode/ExitPlanMode、select_tools）、协作（Agent/AgentSwarm/AskUserQuestion/Skill 递归深度 3）、目标（CreateGoal/GetGoal/UpdateGoal/SetGoalBudget）、后台（TodoList/TaskList/TaskOutput/TaskStop）、定时（CronCreate/CronList/CronDelete）、Web（WebSearch/FetchURL，宿主注入实现才注册）。

路径安全策略（tools/policies/path-access.ts）：纯词法规范化（不 follow symlink）、isWithinDirectory 强制分隔符边界防 /workspace-evil 共享前缀逃逸、默认模式越界绝对路径放行（仅标记 outsideWorkspace）、相对路径逃逸抛 PathSecurityError。

SSRF 防护（tools/providers/local-fetch-url.ts:121）：只允许 http(s)、IP 字面量查私网/回环/ULA 黑名单、DNS lookup all 检查每个解析地址、pinnedLookup 把连接固定到已校验地址集防 DNS rebinding。

#4.8 RPC：同进程模拟网络

createRPC()（rpc/client.ts:31）是同进程双端代理，simulateNetwork 用 setTimeout(0) + JSON.stringify/parse 往返：

  • 强制 payload/返回值 JSON 可序列化——跨进程序列化契约在进程内也被执行，杜绝引用泄漏；
  • 天然的异步边界（调用方拿到的永远是拷贝）；
  • 错误统一 KimiErrorPayload 线格式往返（有意剔除 cause/stack，code 判别）。

类型面：CoreAPI（核心→SDK：事件、审批、问题、工具回调）与 SDKAPI（SDK→核心：prompt/steer/cancel/setModel…）两个方向。

#4.10 其它子系统速览

  • MCP（mcp/connection-manager.ts:129）：状态机 pending → connected | failed | needs-auth | disabled；attemptId 防止过期连接尝试覆盖新状态；Promise.allSettled 失败隔离（一个 server 崩溃不影响会话启动）；OAuth 401 判定 needs-auth + 合成 authenticate 工具。
  • 插件（plugin/manager.ts:39）：本地路径/GitHub/zip 三源安装 → manifest 校验 → 受管目录；能力聚合（enabledMcpServers 改名 plugin__<id>__<server>、enabledHooks 注入 env、enabledCommands 模板展开 $ARGUMENTS）。
  • Hook 引擎（session/hooks/）：Claude Code 风格——spawn shell 命令、stdin 喂 JSON、exit code 2 = block、stdout JSON 结构化输出（permissionDecision:'deny' → block）、30s 默认超时。
  • 后台任务（agent/background/）：三类任务（bash/子代理/question）；内存环形缓冲 1MiB + 磁盘 output.log（权威、永不截断）；16MiB 硬顶超限 SIGTERM→宽限→SIGKILL；重启后 reconcile() 把"磁盘标记 running 但无存活进程"的任务标为 lost。
  • GoalMode：状态机 active/paused/blocked/complete（complete 瞬时态不落盘）；预算（token/turn/wall-clock）；resume 时 active 降级为 paused（磁盘上不可能在跑）。
  • flags：仅 2 个实验开关（tool-select、secondary-model）；FlagResolver 优先级：总开关 env → 单 flag env → config → registry 默认；纯同步实时读 env。
  • 错误体系：KimiError 唯一错误类（判别按 code 字符串）；ErrorCodes 约 70 个 domain.reason 常量；toKimiErrorPayload 归一化任意错误（429→rate_limit、quota 耗尽 429 特判 api_error 防 swarm 重排队死循环、HTML 错误体抽 <title>）。

#4.12 本章小结

  • v1 是 v2 的"上一代内核"，仍服务 SDK 嵌入、ACP 与迁移场景；restoreAgentRecord 甚至能恢复 v2 写出的会话文件。
  • 特色是 VSCode 风格手写 DI 容器（零依赖）：叶子优先构造的构造前环检测 + 防御栈，Proxy 延迟实例化 + 早监听器驻车。
  • loop 被刻意设计为"无状态纯循环"，只通过 LLM、buildMessages、buildTools、dispatchEvent、LoopHooks 五个窄接口与宿主交互。
  • 容错分层精细：step 级退避重试、媒体投影三级降级重发、上下文溢出观测学习后强制压缩——三层防御保证同一段历史不会被 provider 反复拒绝而死循环。
  • 持久化是事件溯源式 wire log：resume 逐条重放重建内存态（不发事件/不调 LLM/不执行工具）。
