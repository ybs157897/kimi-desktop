第 7 章 协议层：线协议、客户端 SDK 与 ACP 桥

研究对象：packages/protocol、klient、node-sdk、transcript、acp-adapter、acp-server。 学习目标：理解 Kimi Code 的"协议层"——一端定义对外线协议的类型与契约，另一端把引擎能力翻译成第三方集成协议（ACP）与宿主 SDK 外观。

#7.1 三组职责

组 包 面向谁
线协议规范 protocol Kimi Code daemon 的 REST + WebSocket 协议 schema 库（纯类型 + 纯 schema，零运行时逻辑）
客户端 SDK 双雄 klient + node-sdk klient 面向 v2 引擎的传输无关客户端 facade（ipc/memory 双传输）；node-sdk 是对外发布的宿主 SDK，把 v1/v2 统一成一套 KimiHarness/Session 外观
ACP 桥 acp-adapter + acp-server Agent Client Protocol（Anthropic 主导的开放协议，Zed/JetBrains 等编辑器用它驱动编码 agent）的两种服务器实现——adapter 桥接 v1 引擎，server 桥接 v2 引擎 
                     ┌────────────────── KAP（线协议，/api/v1 REST + WS）──────────────────┐
   @moonshot-ai/protocol  ── 定义信封/错误码/事件/请求响应 schema（规范源，纯 zod）
        ▲ 镜像（手工同步）
 kap-server/src/protocol/ ── 服务器侧协议拷贝            agent-core(v1) rpc/* ── v1 引擎用 protocol 定义 RPC 线契约
   @moonshot-ai/klient  ── agent-core-v2 的客户端 facade（ipc/memory，契约驱动）
   @moonshot-ai/node-sdk ── 宿主 SDK（v1: agent-core createRPC；v2: klient/memory）
   @moonshot-ai/acp-adapter ── ACP stdio 服务器（v1 引擎）
   @moonshot-ai/acp-server   ── ACP stdio 服务器（v2 引擎，native）
   @moonshot-ai/transcript   ── 转录渲染数据层（被 kap-server 消费）

关键架构事实：

  1. protocol 是"规范源"而非"运行依赖"：v2 引擎链几乎不 import 它（agent-core-v2 只用了 ToolInputDisplay，kap-server 完全用自己的拷贝，klient 仅作 devDependency 做编译期 parity 断言）；真正的运行依赖方是 v1 引擎 agent-core 和 acp-server。
  2. 两代客户端是"同一协议、两个实现"：node-sdk 的 v1 客户端走 createRPC，v2 客户端走 bootstrap() + klient memory——但对外暴露恒定的 v1 协议形状（v1 语义兼容层被完整搬进 node-sdk 的 v2/ 目录）。
  3. 两个 ACP 实现是"迁移产物"：kimi acp 默认走 acp-server（v2），仅 KIMI_CODE_LEGACY_FLAG=1 时回退 acp-adapter（v1）。

#7.2 protocol：线协议 schema

#7.2.1 信封与错误码

所有 REST 响应统一 { code, msg, data, request_id } 信封；okEnvelope 固定 code:0。错误码按十进制前缀分区：0 成功、4xxxx 客户端（40001 校验、40110-40113 认证、40401-40416 not_found、40901-40920 冲突、41301-41305 超限、42902 watch 超限）、5xxxx daemon 内部、6xxxx 工具运行时、7xxxx LLM provider 透传（msg 保留上游原文）、8xxxx MCP 透传。ErrorCodeReason 提供每码的稳定点分字符串。

#7.2.2 消息与会话

  • Message：content 是 7 种块的判别联合（text/tool_use/tool_result/image/video/file/thinking）；file 块只带元数据，字节永远走 /files 通道。
  • Session：busy（任一 agent 有活跃 turn）取代了旧的五值 status 枚举——awaiting 状态改由 approval/question 通道表达，turn 结果由 turn.ended 事件表达，"客户端自行组合呈现"。
  • ToolInputDisplay 14 种 / ToolResultDisplay 12 种：工具调用如何呈现在 UI 上的协议化描述；plan_review 的 options 直接承载 ExitPlanMode 的审批选项。

#7.2.3 事件（events.ts，1939 行，本包最大文件）

TS 接口层 51 种事件（AgentEvent 判别联合 + Event = AgentEvent & {agentId, sessionId}），每组 zod schema 用 satisfies z.ZodType<...> 钉住同步：

  • turn 生命周期：turn.started（带 PromptOrigin 13 种来源）、turn.ended（reason: completed/cancelled/failed/blocked）、turn.step.*（step.completed 带 LLM 延迟四分拆：llmFirstTokenLatencyMs 拆 client 构建 vs server 首 token，llmStreamDurationMs 拆 server decode vs client consume）；
  • 流式增量：assistant.delta/thinking.delta/tool.call.delta/tool.call.started（带 display）/tool.progress/tool.result；
  • agent 状态：agent.status.updated（AgentPhase 8 态判别联合：idle/running/streaming/tool_call/retrying/awaiting_approval/interrupted/ended）——UI 渲染"agent 正在干什么"的权威来源；
  • 任务/会话/全局：task.* + 旧名 background.task.* 别名、session.work_changed、workspace.*、model_catalog.changed（带 per-provider diff）、goal.updated、compaction.*、cron.fired、hook.result、mcp.server.status、error（KimiErrorPayload）。

volatile 分类：VOLATILE_EVENT_TYPES 列 8 种瞬态事件（三个 delta、tool.progress、shell.*、agent.status.updated）——不 journal、不推进 seq、断线不重放（已标记 deprecated，分类权移交 kap-server）。

#7.2.4 WS 控制面（ws-control.ts）

WS_PROTOCOL_VERSION = 2（IM 式多端同步）：游标 {seq, epoch}、seq 持久化、volatile 事件带 volatile:true、resync_required 增 epoch_changed 原因。三类帧：事件帧（offset 是流式 delta 的累计字符偏移，客户端按 snapshot.in_flight_turn.*_text.length 对齐去重）、控制帧（12 种操作）、ACK 帧。所有操作以 WsOperationDefinition 表驱动——asyncapi.ts 从同一张表生成 AsyncAPI 3.1.0 文档。

#7.2.5 快照-订阅恢复协议（rest/snapshot.ts）

① GET /sessions/{sid}/snapshot（原子于水位 as_of_seq，含 in_flight_turn 的流式累计态）→ ② WS subscribe 带 cursors[sid]={seq: as_of_seq, epoch} → ③ 应用 seq > as_of_seq 的后续 durable 事件。"无缺口无重复 by construction"；offset 字段让客户端对 volatile delta 做累计偏移对齐：offset < 本地长度 为重复（跳过），offset > 本地长度 为丢帧（重新快照）。

#7.3 klient：契约驱动的 v2 客户端

分层铁律（AGENTS.md）：Facade（唯一公共 API，禁止 service locator）→ Contract（zod 全量 schema）→ KlientChannel（唯一传输 SPI）→ ipc / memory。

facade.method(args)
  → ScopedCaller 查 globalContract[service][method]
  → parseInput → channel.call(scope, service, method, wireArgs)
       ├─ ipc: trimTrailingUndefined → unix socket NDJSON ──▶ host.handleFrame
       └─ memory: dispatcher.call → resolveScope → accessor.get(token)[method]
  → wireClone(result)（memory 侧模拟 JSON 边界；ipc 天然 JSON）
  → parseOutput → 返回
  • KlientChannel（core/channel.ts:35）：call(scope, service, method, args) / stream / listen / close；ScopeRef { workspaceId?, sessionId?, agentId? }（空对象 = core/app scope）。
  • scope 解析语义（memory dispatcher）：workspaceId → handlerFor；sessionId → getLiveSessionById；agentId==='main' → ensureMainAgent(session) 现场物化；其他 → IAgentLifecycleService.get()。
  • 双传输字节一致性：memory dispatcher 对每个入参/返回值/事件载荷过 wireClone = JSON.parse(JSON.stringify(v))——in-process 消费者与跨 socket 消费者观察到完全相同的形状，非序列化泄漏提前失败。
  • JSON 无 undefined 的三处处理：trimTrailingUndefined 裁掉尾部可选参数（否则跨 wire 变 null 顶掉引擎默认参数）；maybe()/noResult 归一 null-vs-undefined 双态；config.replace 把 undefined 显式编码为 null（"清空该域"语义）。
  • 契约即 drift tripwire：test/contract-parity.ts 用 AssertWire（双向）/AssertEngineToWire（单向）在编译期钉住"引擎类型 ↔ wire schema"——引擎类型一改，tsc 先红。这是 klient 不 import protocol 却能保持线形状一致的机制。
  • 无自动重连：ipc socket 关闭即 failAll()（注释明说"WS 传输才拥有可恢复连接的故事"）。

#7.4 node-sdk：双引擎统一宿主 SDK

SDKRpcClientBase（rpc.ts:144，约 80 个方法的 v1 RPC 外观基类）是骨架，两个子类：

  • SDKRpcClient（v1）：agent-core 的 createRPC 进程内 RPC 对 + new KimiCore。
  • SDKRpcClientV2（sdk-rpc-client-v2.ts，2258 行）：bootstrap() 出 agent-core-v2 Scope → createKlient({scope})（memory 传输，仍穿契约校验 + JSON 往返）→ 每个 v1 方法 override 成 v2 服务调用。文件头注释即迁移清单；未迁移方法抛 not_implemented。

KimiHarness 是宿主顶层门面；Session（session.ts，789 行）是单会话门面。v2/ 目录 6 个映射层：event-mapper（v2 DomainEvent → v1 Event，丢弃 10 种 v2-only 类型）、session-wiring（每活会话一份：agent bus 订阅 + pending interaction 三路桥）、session-mapper/config-mapper、global-mcp、resume-replay（一次性 v1 Agent 折叠 wire.jsonl，跑在只读内存 persistence 上）、import-context。

审批的 v1 push vs v2 pull 桥：v1 引擎同步调 requestApproval；v2 引擎把审批"停放"在 interaction kernel，onDidChangePending 通知后由桥拉到同一条 base.requestApproval（继承 v1 的 no-handler 取消语义），结果写回 decide(id, response)——kernel 对已非 pending 的 id 是 no-op，取消后迟到回答安全。

#7.5 transcript：转录渲染数据层

四层架构：

层 职责
L1 AgentTranscript（单 agent 聚合态，apply() 批量收敛 + 单次 onChange）/ TranscriptStore（session 根）
L2 14 种 op（turn.upsert/step.upsert/frame.upsert/append/items.remove/marker/task.upsert/interaction.upsert/removal/prompt.upsert/meta.merge/reset/undo/clear）——append 是唯一非幂等 op；纯函数 copy-on-write reducer
L3 TranscriptGradeSpec（'*' 通配 + agent 覆盖，needsResetOnTransition 仅升级需 reset）+ 按 op 种类裁剪的粒度过滤
L4 视图注册表（view/origin.kind/marker/task.kind 四类 key）

领域模型：turn 是自然键 t<ordinal>、step t3.2、frame t3.2.f4；frame 是叶子渲染单元（text/thinking/tool_call/notice），从不嵌套，靠 taskId/approvalId/todoId/agentRefs 交叉引用；interaction（审批/提问）永不进分页时间线。

live:  engine IEventBus → AgentTranscriptProjector.map() → ops[]
         → AgentTranscript.apply()（L1 唯一收敛路径，gap 捕获）
         → onChange → TranscriptService.journalOps（每批 +1 seq）→ 广播
         → 按连接粒度 filterOpsForGrade 扇出 → WS transcript.ops（volatile）
cold:  wire.jsonl → groupMessagesIntoSnapshot + foldWireRecordFacts
         → 以幂等 upsert 序列灌入 live store（绝不 reset，防覆盖直播 ops）

工程细节：

  • 幂等机制：每个 upsert 前做深度字段等价比较（turnEquals/stepEquals/frameEquals），相等返回 changed:false——去重与"onChange 只发真变更"的依据。
  • append 四态对齐（appendAtOffset）：offset > 本地长度 → gap（重新快照）；已完整包含 → 重复；部分重叠且一致 → 裁剪 novel 后缀合并；重叠不一致 → gap——分流式流，绝不静默重写丢弃本地内容。
  • 骨架自动补全：skeletonTurn/skeletonStep 让 upsert 即使父级未到也能落地；但 append 找不到父 frame 返回 gap。
  • 粒度过滤"降级安全"：只按 op 种类门控；安全性依据是 producer 在 step/turn 完成边界重发整帧 flush upsert，低粒度客户端自然重收敛。
  • 崩溃 == cancelled：冷重建扫描结束仍 pending 的 interaction 一律置 cancelled，防幽灵 pending。
  • op-batch seq 契约：per-(session, agent) 单调批次号，每派发一批 +1（非每 op）；seq 全部 optional——缺省即 pre-seq 旧协议。

#7.6 ACP 桥：同一 ACP 表面、两代引擎实现

两包模块一一对应（server/session/events-map/convert/approval/question/modes/slash/config-options/model-catalog/auth-methods/version），差异在接入面：

  • acp-adapter（SDK ^0.23）：AcpServer implements Agent，会话经 harness.createSession({kaos, mcpServers}) 驱动 v1 引擎；AcpKaos 装饰 LocalKaos，readText/writeText 走 ACP fs/readTextFile/writeTextFile 反向 RPC（覆盖 Zed 未保存缓冲）。
  • acp-server（SDK ^1.3）：组合根按 bootstrap() → createKlient({scope}) → app.connect(stream) 装配；acp-fs 在 Session scope 注册影子 IHostFileSystem；acp-terminal 在 Agent scope 注册影子 ISessionProcessRunner（Bash 调用判别四元组 args.length===3 && args[1]==='-c' && NO_COLOR==='1' && TERM==='dumb'）。

TurnDriver 状态机（server session.ts:150-175）：

prompt → driveLaunch
  ├─ launched === undefined → 无 turn（hook-blocked）→ 立即结算 end_turn
  ├─ launched.turn_id 落地 → 若 cancelRequested 补发精确 cancel({turnId})（幂等）
  │       然后回放 early 缓冲中 turnId 匹配的事件（快 turn 先于 launch 返回结束）
  └─ launch reject → mapPromptLaunchError
turn.ended(匹配) → settleDriver 一次 → resolve({stopReason}) / reject

工具调用 wire 侧生命周期（顺序修复是两包最出彩的防御）：

provider 流式 args → tool.call.delta（先到！）→ LAZY-CREATE tool_call(status:pending)
  → 后续 delta → tool_call_update（累积 REPLACE 语义 args 全文）
tool.call.started（后到）→ 已存在 → "upgrade" update（补 title/kind/rawInput, status→in_progress）
tool.progress → tool_call_update(title 刷新)
tool.result → tool_call_update(completed/failed, content=结果)
wire id 前缀 `${turnId}:${rawId}`（模型 retry 复用 rawId 也不冲突）

为什么必须懒建：引擎的 tool.call.delta 先于 tool.call.started 到达（delta 来自模型参数流，started 来自循环派发）——naive 映射会让 tool_call_update 先于 CREATE 上 wire，Zed 报 "Tool call not found"。

其它防御：

  • tool_call_update 的 REPLACE 语义：ACP 的 content 是整块替换，delta 累积器每次发累积 args 全文，started 时用完整 stringifyArgs 重置种子；stringifyArgs 对 BigInt/循环结构回退 String()——流式路径永不 crash。
  • fail-safe 原则：未知 approval optionId → rejected；反向 RPC 失败 → rejected/null（宁可拒绝不可误批）；notification 错误只能 log 不能抛。
  • 错误映射防泄漏：auth.login_required → RequestError.authRequired()（客户端自驱 re-auth）；其余 → internalError，细节只进日志。
  • busy 本地拒绝：v2 引擎对活跃 turn 的 agent.prompt 会排队且返回 undefined（与 hook-blocked 不可区分），放行会覆盖唯一 driver——故同步抛 -32600（turn.agent_busy）。
  • 终端输出去重：terminal-backed 工具调用的卡片只放 {type:'terminal'}（模型仍收全文）；HideOutputMarker 哨兵让文本输出短路为 [] 防双渲染。

#7.8 本章小结

  • protocol 在 v2 时代从"运行依赖"降级为"规范源/历史档案"——协议事实上的权威已漂移到"引擎服务接口 + kap-server 实现"。
  • klient 是契约驱动 facade + 唯一 KlientChannel SPI（ipc/memory 双传输），memory 侧用 wireClone 保证两传输字节级一致；编译期 parity 断言钉住引擎类型与 wire schema 同步。
  • node-sdk 是"v1 语义兼容层"：6 个纯映射层把 v2 引擎差异全部消化在 SDK 内，对外暴露恒定 v1 协议形状。
  • 两个 ACP 实现围绕三类协议陷阱（流式事件乱序、REPLACE 内容语义、notification 不能报错）做了系统性防御；kimi acp 的 legacy flag 是迁移期总开关。
