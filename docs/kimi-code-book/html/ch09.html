第 9 章 基础设施：认证、遥测、执行环境与调试

研究对象：packages/oauth、telemetry、kaos、migration-legacy、tree-sitter-bash 与 apps/kimi-inspect。 学习目标：理解支撑认证、观测、执行环境、旧版迁移、命令安全分析与运行时调试的六个底座单元。

#9.1 六个单元的分类

类别 包 一句话职责
身份与观测 oauth Kimi OAuth（RFC 8628 设备码流）与"managed auth"全套：token 生命周期、托管配置下发、用量/用户信息/反馈 API 客户端
telemetry 客户端遥测：事件缓冲、批量上报、崩溃捕获、磁盘失败持久化
执行与解析 kaos Kimi Agent OS——对本地进程/文件系统（以及可选的 SSH 远程环境）的统一执行抽象
tree-sitter-bash 纯 TS 手写 bash 解析器（无 wasm），用于 agent 的 shell 命令权限分析
迁移 migration-legacy 把旧版 kimi-cli（~/.kimi/）的数据安全迁移到 kimi-code（~/.kimi-code/）
调试 kimi-inspect kap-server /api/v1/debug RPC 反射面的 Web 检查器

#9.2 oauth：全 repo 被引用最广的基础包

三层结构：纯 HTTP 层（oauth.ts）、状态管理层（oauth-manager.ts + storage.ts + token-state.ts）、托管编排层（toolkit.ts + managed-*.ts）。

#9.2.1 设备码登录时序

KimiOAuthToolkit.login()
  └─ OAuthManager.login(15min 本地预算)
        ├─ POST /api/oauth/device_authorization {client_id} + X-Msh-* 设备头
        ├─ 轮询循环（interval 秒）：
        │    authorization_pending → sleep(interval) 继续
        │    slow_down → interval += 5s 继续
        │    expired_token → 重新请求 device_authorization
        │    access_denied → 抛错
        │    成功 → TokenInfo {accessToken, refreshToken, expiresAt}
        └─ storage.save('kimi-code', token)   ← 0600 原子写

provisionManagedKimiCodeConfig()
  GET {base}/models  (Bearer accessToken)
  → 解析 ManagedKimiCodeModelInfo[]（context_length/supports_*/think_efforts）
  → adapter.apply(): config.providers['managed:kimi-code'] = {type:'kimi', oauth:{...}}
    + config.models['kimi-code/<id>'] = alias（能力推导）
    + config.defaultModel / config.thinking.enabled + config.services
  → atomicWrite config.toml（0600）

托管认证的核心：登录后自动拉取 /models 把云端模型目录物化进 config.toml——用户不需要自备 API key。

#9.2.2 token 生命周期与刷新协调（并发安全核心）

FileTokenStorage 三态：valid | revoked(墓碑) | missing
ensureFresh(force=false):
  load → missing → throw OAuthUnauthorizedError("Run /login")
       → revoked → throw OAuthUnauthorizedError("re-login required")
       → valid 且 remaining > max(300s, expiresIn*0.5) → 直接返回
       → valid 且需刷新 → acquireRefreshLock()  ← proper-lockfile 跨进程锁
            ├─ 锁后重读 storage：
            │    revoked → 抛；missing → 用锁前快照
            │    valid 且不再需刷新 → 用 peer 的 token（返回别人的结果）
            ├─ refreshAccessToken → save → return
            └─ catch OAuthUnauthorizedError：
                  sleep(100ms) 后重读 storage：
                    peer 已轮换 refresh_token → 用 peer 的（stale-token 竞态）
                    否则 → save(revokedTombstone)  ← 让新进程看到"需重登"
  • 401 竞态恢复：刷新拿 401 后先 sleep(100ms) 重读存储，若 peer 进程已轮换 refresh_token 则用 peer 的新 token——把"凭据真失效"与"并发轮换竞态"区分开；确认失效才写墓碑。
  • 墓碑设计：刷新被 401 后不是删文件而是写空 token 记录——新进程能看到"曾经登录过、现在需要重登"而非"从未登录过"。
  • 凭据槽位哈希（resolveKimiCodeOAuthKey）：默认环境用固定键 oauth/kimi-code；任何环境覆盖都派生 oauth/kimi-code-env-<sha256:16>——"写入槽位永远等于读取槽位"，防止环境切换导致凭据混用。
  • 跨进程锁：proper-lockfile，stale: 5s 处理崩溃残留；Windows 与 KIMI_DISABLE_OAUTH_LOCK=1 禁用锁但仍保留"锁后重读"兜底。
  • isManagedKimiCodeBaseUrl：URL 按 origin+pathname 规范化严格比对——代理/网关/自托管镜像不会被自动刷新（其 /models schema 不可信）。
  • 模型别名选择性合并：上游字段集合内覆盖、集合外（用户手写）保留；刷新时上游消失的模型删除。

#9.3 telemetry：管道式五段

client(track) → sink(缓冲/富化) → transport(HTTP上报/磁盘兜底)
      ↑ queue(启动前预缓冲)        ↑ systemMetricsCollector / crash handler
  • TelemetryClient：全局单例 + ScopedTelemetryClient（withContext 派生）；track 时 sink 未挂接则进内存队列（上限 1000 条，溢出丢最旧）。
  • EventSink：每事件注入静态 context（app_name/version/runtime/platform/ci/locale/ui_mode/model/build_sha）；缓冲满 50 条或每 30s flush。
  • AsyncTransport：POST telemetry-logs.kimi.com/v1/event，401 剥掉鉴权头重试一次；429/5xx 按 [1s,4s,16s] 退避；最终失败 saveToDisk 写 failed_<rand>.jsonl（0600）；下次启动 retryDiskEvents 补发（>7 天删除）。事件名统一加 kfc_ 前缀。
  • crash.ts：uncaughtExceptionMonitor（不干扰默认崩溃行为）+ unhandledRejection 监听（记录后按"是否唯一监听者"决定是否 rethrow 以保留 Node 默认行为）；CrashPhase 区分 startup/runtime/shutdown；AbortError 一律不报。
  • systemMetrics.ts：启动 1.5s 暖采样 + 每 5 分钟一个 system_metrics 事件。

遥测永不致命：所有上报路径 catch 吞错；flushSync 兜底磁盘；crash 事件先 flushSync 再让原异常继续传播。

#9.4 kaos：Kimi Agent OS

Kaos 接口模拟 Python os/pathlib 语义：路径（normpath/gethome/getcwd）、目录（chdir/withCwd/iterdir/glob）、文件（readBytes/readText/readLines/writeBytes/writeText/mkdir）、进程（exec → KaosProcess）。

LocalKaos 关键设计：

  • 每实例独立 _cwd（不碰 process.cwd()，多实例可并存）；withCwd/withEnv 返回新实例（不可变风格）。
  • exec 用 detached:true 使子进程成为进程组组长，kill 用 process.kill(-pid) 杀整组（Windows 走 taskkill /T /F）；pid≤0（spawn 失败）拒绝 kill 防 kill(-1) 误杀全组。
  • waitForSpawn 竞速：spawn 后必须等 'spawn' 事件再返回——否则向"从未存在的进程"写 stdin。
  • glob：手写 ** 展开 + (dev,ino) 环检测（ino=0 的文件系统——FAT/exFAT——放弃检测，否则所有目录互相"访问过"而全部跳过）。
  • UTF-8 严格校验器：手写 DFA（E0/ED/F0/F4 边界特判），流式解码保证不把多字节字符切成两半。
  • 登录 shell PATH：用 $SHELL -l -c /usr/bin/env 提取并只追加当前 PATH 缺失的绝对路径项——空/./相对项都是 cwd 依赖查找（安全考量）；用绝对路径 /usr/bin/env 执行（防仓库里被植入的 env）。
  • SSHKaos（/ssh 子路径）：ssh2 + SFTP 实现同一接口；shellQuote 单引号包裹防注入；远程 cwd 用 cd <dir> && ... 前缀模拟；进程树 kill 用递归 pkill -P。
  • current.ts：AsyncLocalStorage 绑定当前 Kaos 实例——工具层代码无需处处传递 kaos 对象。

#9.5 tree-sitter-bash：永不抛异常、预算封顶的解析器

parse(source, {timeoutMs=50, maxNodes=50_000}) → {ok:true, rootNode, hasError} | {ok:false, reason:'aborted'}。永不抛异常——内部 bug 被兜底为 program+ERROR 降级树（ok:true + hasError）。

为什么这样设计：它是 agent-core-v2 执行 shell 命令前的权限判官（app/bashParser/ 服务）——权限判断不允许被解析器故障卡死；abort 或解析器 bug 都产出"可用的降级树"。

parse(source, {timeoutMs, maxNodes})
  → ParseBudget（deadline + 节点配额）
  → Lexer 惰性 token 流（peek/next/reposition + heredoc 队列）
  → parseStatementList(';'/'&'/换行/注释/ERROR 恢复)
      → parseList(&&/||) → parsePipeline(|/|&) → parseStatementCore
          → parseCommand（赋值前缀识别）
          → parseCompoundGuarded（if/while/for/case/函数定义）
          → parseSubshell / $() → parseScopedStatements（depth+1）
          → [[ ]] → Pratt parseExpression
          → heredoc → completeHeredocs 事后扩展祖先 end
  → materialize（Frame → SyntaxNode 两趟迭代，不 tick）
  → {ok:true, rootNode, hasError} | {ok:false, reason:'aborted'}
  • 确定性预算：tick 只挂在节点创建（maxNodes 配额），progress 挂在长扫描循环（每 2048 字符）——病态单 token（几百 KB 未终止引号）也能按时撞线且不虚增节点。封顶总工作量而非输入大小：500KB heredoc body 只有几个节点可正常解析；百万级 case 触发节点上限被 abort。fuzz 测试断言 400KB 节点炸弹 <100ms abort。
  • 多深度上限防爆栈：MAX_PARSE_DEPTH=500、MAX_SUBSTITUTION_DEPTH=150（每次 $() 新 Parser 约 13 栈帧/层，实测 380-500 层爆栈，150 留 2.5 倍余量）、lexer MAX_SCAN_DEPTH=1024。
  • case 歧义双保险：lexer 层 scanBalancedStatements 维护 caseDepths[] 栈（case item 的 ) 是 pattern 闭合符）；parser 层 scanCasePatternEnd 逐字符扫 pattern（extglob 组括号在 token 流中不可表示）+ lexer.reposition 回卷。
  • 与官方 tree-sitter-bash 的差分被 fixture 钉住：80 处 @known-diff 对照官方 wasm 的双向校验；<> 操作符官方 0.25.0 解析失败这里支持。

#9.6 migration-legacy：检测 → 提示 → 执行

detectMigration: 扫描 ~/.kimi/（config.toml/mcp.json/user-history/credentials/...）
  → marker 抑制检查（.migrated-to-kimi-code / .skip-migration-from-kimi-cli）
  → 两层提示 → resolveMigrationScope
  → runMigration（五步）：
      config → mcp → userHistory → skills → sessions
  → migration-report.json + migration-errors.log（追加式，跨 run）
  → marker 写入（sessionsFailed 为空时才写，允许重试）

migrateOneSession 内部：目标目录已存在时分类 imported|foreign|debris（有 custom.imported_from_kimi_cli 标记 = 上次自己写的 → 幂等跳过；无标记 → 真冲突；state.json 缺失/损坏 → debris 删除重迁）。翻译 context.jsonl → NormalizedMessage → closeDanglingToolCalls → 写 agents/main/wire.jsonl + state.json；最后 utimes 把文件 mtime 还原成原始 wire_mtime——SessionStore.list 按文件系统 mtime 排序，不还原就会把迁移时间戳当成会话时间，--continue 顺序全乱。

关键决策：

  • OAuth 凭据刻意不迁移：refresh token 服务端轮换，复制会让两个安装互相踢下线——用户必须重新 /login。
  • 悬空 tool call 合成占位：kimi-core 的 context 模块在 tool 交换未闭合时延迟后续所有消息——closeDanglingToolCalls 为每个未满足的 toolCallId 插入 [tool result unavailable] 占位结果，保持消息顺序。
  • 冲突降级为兄弟文件：目标配置无法解析或用户改过时，迁移结果写到 *.migrated-from-kimi-cli.* 兄弟文件，绝不覆盖用户数据。
  • schema 白名单跟随上游：SUPPORTED_TOP_LEVEL_KEYS 从 KimiConfigSchema.shape 动态推导——上游加键自动跟。

#9.7 kimi-inspect：debug 反射面的官方客户端

kimi-inspect 与 kap-server 之间是一套自研 RPC 传输层（VS Code ProxyChannel 模型）：

  • DI decorator id 即 wire 通道名（service = String(decoratorId)）；channels.ts 拉全量协议（GET /api/v1/debug/channels，无白名单）并 serviceByName 反向物化 proxy；errors.ts 的 RPCError 用数字 code 做跨线分支键。
  • JS Proxy 把属性访问变成 channel.call；方法 → async 调用、onXxx → 事件、普通成员 → 零参属性读。
  • 服务器发现：Vite dev server 的 GET /__inspect/servers 扫本机 kap-server 实例注册表（~/.kimi-code/server/instances/*.json，pid 存活过滤）与共享 bearer token；探针先 GET /api/v1/debug/channels 验证表面存在，失败渲染阻塞错误屏。

transcript 增量对账（唯一的"复杂状态"）：初始 REST 全量 + WS 增量 + seq 水位对账——WS 帧是 volatile 的（从不入 durable journal），可靠性靠 op-batch seq：断线错过的批次由 transcript_since 游标 / ops?since_seq= 点对点补齐，complete:false 则全量 REST 刷新；四路触发（resync/ack/seq 缺口/append gap）汇入同一 catchUp。store 复用 @moonshot-ai/transcript 的 applyOperation reducer——零重实现。

其他亮点：

  • WS 握手：浏览器无法自定义 header，token 通过 kimi-code.bearer.<token> 子协议呈现；ack 是流挂载的精确时刻（重连后在此刻而非 open 触发 reconcile）。
  • audit diff 的引用相等快速路径：copy-on-write reducer 下未动子树共享引用，直接判 unchanged 免遍历。
  • 虚拟化零依赖：content-visibility: auto + contain-intrinsic-size，浏览器原生虚拟化超长会话。

#9.9 本章小结

  • oauth 的核心不是协议本身而是"托管 auth"编排：设备码登录后自动拉取 /models 把云端模型目录物化进 config.toml；并发安全靠跨进程锁 + 锁后重读 + 401 竞态恢复，失效时写墓碑而非删文件。
  • kaos 是"模拟 Python os/pathlib 语义"的执行抽象：实例级 cwd、detached 进程组 kill、(dev,ino) glob 环检测、手写 UTF-8 DFA——本地与 SSH 实现可互换。
  • tree-sitter-bash 是"永不抛异常、预算封顶"的权限判官：封顶总工作量而非输入大小，abort 或解析器 bug 都产出可用的降级树。
  • kimi-inspect 是 kap-server debug 反射面的官方客户端：DI decorator id 即 wire 通道名，transcript 通道靠 op-batch seq 水位做"WS 增量 + 断点补拉 + 全量回退"三态对账。
